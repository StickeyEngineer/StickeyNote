## 1. Review and commit the release preparation

Run commands from the repository root. Review the changes, then commit:

```sh
git diff --check
git diff
git add Config/App-Info.plist StickeyNote.xcodeproj/project.pbxproj \
  scripts/generate-project.py scripts/release-mac.sh README.md \
  docs/releases/v1.0.1.md docs/releases/v1.0.1-checklist.md
git commit -m "Prepare Stickey Notes v1.0.1 release"
```

The local `origin` uses the former `AmirDoreh/StickeyNote` URL; GitHub resolves it to the same repository. Update the URL before pushing:

```sh
git remote set-url origin git@github.com:StickeyEngineer/StickeyNote.git
```

## 2. Archive locally

Ensure Xcode's Apple account can sign for team `8ZA2YW2U9D`. If Xcode reports an expired session, sign in again in **Xcode → Settings → Accounts**. If it reports an agreement update, the team's Account Holder must accept it in the [Apple Developer account](https://developer.apple.com/account).

```sh
zsh scripts/release-mac.sh archive 1.0.1
```

Archive: `build/release-v1.0.1/StickeyNote.xcarchive`.

If this archive was already successfully prepared from the current source, continue to submission. The script refuses to overwrite an existing archive. If app code or build metadata changes, move the existing `build/release-v1.0.1` directory to a backup location and rebuild; do not publish an older binary with a newer source tag.

## 3. Sign and notarize with Apple

The Xcode account needs Developer ID access. Use the team's Account Holder account, or an Admin granted cloud-managed Developer ID signing access. This stage uploads the archive to Apple:

```sh
zsh scripts/release-mac.sh submit 1.0.1
```

Open the archive in Xcode to follow notarization status or inspect errors:

```sh
open build/release-v1.0.1/StickeyNote.xcarchive
```

Wait for Apple to accept notarization. If submission fails, resolve the reported account, signing, or notarization error and rerun the stage. Preserve the team, bundle identifier, and Keychain group. The archive's development signature is not the public distribution signature.

## 4. Package the public download

```sh
zsh scripts/release-mac.sh package 1.0.1
```

Packaging verifies Apple silicon and Intel binaries, version, Developer ID signature, hardened runtime, timestamp, distribution provisioning, Keychain entitlements, notarization ticket, and Gatekeeper acceptance. It creates assets only after verification succeeds:

- `build/release-v1.0.1/Stickey-Notes-v1.0.1-macOS-universal.zip`
- `build/release-v1.0.1/SHA256SUMS.txt`

Verify the checksum:

```sh
(cd build/release-v1.0.1 && shasum -a 256 -c SHA256SUMS.txt)
```

## 5. Test the packaged app

Extract the generated ZIP and test that exported app. Quit any older instance before launching it. Back up your notes first, and keep the prior app available while checking the upgrade.

- [ ] Confirm About/version metadata shows **1.0.1 (2)** and existing notes, groups, and desktop positions remain available.
- [ ] Unlock an existing Apple-locked note, create a new locked note, cancel an authentication prompt, and verify auto-lock still works.
- [ ] Relaunch with floating notes open; resize and edit them without a crash.
- [ ] Select multiple notes, select all within a search/filter, drag the selection into a group, bulk delete, and restore.
- [ ] Check bulk lock/unlock and cancellation; older PIN/password locks should be skipped by bulk unlock and still open individually.
- [ ] Switch Light/Dark/Auto and relaunch to check persistence.
- [ ] Edit/click website and email links; verify one click opens one destination.
- [ ] Test checklist Return, Command-Return, Command-Up/Down, and deletion of an empty item.
- [ ] Check a fresh installation and, where available, run on both Apple silicon and Intel hardware. A universal binary check alone does not exercise both machines.

## 6. Push the exact source and tag

After the packaged app passes, ensure the working tree has no uncommitted release changes. Commit any final changes and rebuild if app code or build metadata changed. Then, from `main`:

```sh
git status --short
git push origin main
git tag -a v1.0.1 -m "Stickey Notes v1.0.1"
git push origin v1.0.1
```

Do not proceed past a failed push or tag command. If `main` has moved remotely, reconcile the changes, validate and rebuild the resulting source before tagging. Keep the existing v1.0.0 tag unchanged.

## 7. Create and publish the GitHub release

1. Open [Draft a new release](https://github.com/StickeyEngineer/StickeyNote/releases/new).
2. Select the existing **v1.0.1** tag. Set the title to **Stickey Notes v1.0.1**.
3. Paste [v1.0.1.md](v1.0.1.md) into the description.
4. Attach the app ZIP and `SHA256SUMS.txt` from step 4. Save a draft while reviewing.
5. Leave prerelease unchecked, select **Set as latest release**, and publish after both uploads finish.
6. Open the published release, download its ZIP and checksum, verify the checksum again, and check that the app opens normally.

GitHub CLI is not installed on the preparation machine; these browser steps need no CLI installation.
